# FoodLab

Русскоязычное адаптивное приложение для персонального питания на Next.js 16, React 19, TypeScript и Tailwind CSS 4. Работает без платного ИИ и без сервера БД в локальном режиме. В текущей облачной среде включён собственный экземпляр Supabase Auth + PostgreSQL с RLS. Доступ к аккаунту supabase.com не требуется.

## Запуск

Требуется Node.js 22+ (проверено на 24) и npm.

```sh
cd /workspace/food
npm ci
npm run supabase:start
npm run dev
```

Production:

```sh
npm run build
npm start
```

Порт по умолчанию 3000; другой порт: `npm run dev -- --port 3001`. Для установки PWA на iPhone: опубликуйте по HTTPS, откройте Safari → «Поделиться» → «На экран Домой». Service worker включён только в production. После первого посещения оболочка и загруженные JS/CSS доступны офлайн; дополнительные внешние фотографии и Supabase требуют сети. Главная иллюстрация хранится локально; при недоступности внешнего фото карточка использует её как иллюстративную замену. Локальный профиль работает офлайн. Облачные записи не ставятся в офлайн-очередь: ошибка сохранения видна, доступны повторная запись и экспорт.

Webpack выбран явно: служебные сокеты Turbopack блокируются в некоторых облачных песочницах. `experimental.useTypeScriptCli: false` использует поддерживаемый API TypeScript: в этой среде дочерний CLI возвращает пустой stdout. Проверка типов в сборке включена.

## Реальные возможности MVP

- Семь разделов, мобильная навигация, карточки и модальные окна с управлением фокусом.
- 20 начальных рецептов: состав, сырые съедобные массы, шаги, техника, примерные стоимость/выход/КБЖУ, температура готовности мяса.
- Поиск, категории, подбор с учётом техники, времени, сложности, исключений, аллергенных категорий, запасов и истории оценок.
- Создание и редактирование собственных рецептов, правки исходных блюд, удаление из каталога. Правки сохраняются как пользовательские версии; удалённые блюда остаются доступны для расчёта истории съеденного.
- Масштабирование всех ингредиентов и выхода на 1–100 порций. Пищевая ценность из ингредиентов, редактирование источников, фактического выхода и данных этикетки.
- Избранное, оценка 1–10 (0 — не оценено), реакции, причины, заметки и отметка «приготовлено».
- Недельный план: автоматический разнообразный подбор, добавление/изменение/удаление блюд и порций, переключение недель, КБЖУ и оценка стоимости по расходу.
- Отдельный дневник фактически съеденного: запись из меню на текущую дату, удаление ошибочной записи. План и приготовление не увеличивают съеденные калории.
- Список покупок: объединение названий и единиц, однократное вычитание действующих запасов при генерации из выбранной недели, группы, ручные товары, правки количеств, удаление, отметки и копирование текста.
- Продукты дома: создание/редактирование/удаление, единица и необязательная дата годности.
- Профиль с целями и ограничениями, редактируемый список техники.
- Сохранение между сессиями в localStorage; экспорт/импорт валидируемого JSON.
- Подготовленная облачная авторизация по почте и CRUD одного приватного документа состояния в PostgreSQL.

## Структура и модель данных

- `lib/types.ts` — модель предметной области: `Recipe` → `Ingredient[]`, отдельные `Meal[]` для плана и факта, `Feedback`, `PantryItem`, `ShoppingItem`, `Profile`.
- `lib/domain.ts` — чистые расчёты, агрегация покупок, рекомендации и автоплан.
- `lib/catalog.ts` — начальные рецепты и явно оценочные пищевые данные.
- `lib/validation.ts` — валидация рецептов, состояния и импорта (Zod).
- `lib/storage.ts` — localStorage и Supabase, последовательная запись с задержкой, статусы ошибок. Локальные и облачные данные изолированы.
- `components/` — интерфейс приложения, рецепт и PWA-регистрация.
- `supabase/schema.sql` — таблица `foodlab_states(user_id, payload jsonb, updated_at)`, внешний ключ на Auth и четыре owner-only RLS-политики.
- `lib/ai.ts` — контракт будущего серверного генератора. Провайдер пока не подключён, запросов и оплаты нет.

Для MVP профиль хранится одним документом JSONB на пользователя. Все сущности редактируются и сохраняются реально. Это позволяет атомарно сохранять план вместе с рецептами. Совместное редактирование с нескольких устройств пока использует последнюю запись; нет realtime, разрешения конфликтов и серверной истории изменений. Для роста следует выделить нормализованные таблицы `recipes`, `ingredients`, `recipe_ingredients`, `feedback`, `meal_plan`, `consumption`, `pantry`, `shopping_items` с `user_id` и аналогичными RLS-политиками.

## Supabase уже включён в текущей среде

Запущены официальные PostgreSQL, GoTrue (Supabase Auth) и PostgREST. Это self-hosted экземпляр в этой облачной среде, а не управляемый проект на supabase.com. В приложении откройте «Профиль и настройки» → «Зарегистрироваться», задайте свою почту и пароль от 12 символов. Конфигурацию БД, ключи и SQL вручную вводить не нужно.

Данные доступны через `/supabase` на том же адресе, что и FoodLab; внутренние порты Auth/REST слушают только loopback, порт PostgreSQL наружу не опубликован. Шлюз разрешает только нужные пользовательские Auth-операции и таблицу `foodlab_states`; административные API не открыты. Service-role ключи и пароль БД в браузер не передаются. Анонимный ключ публичен; доступ к данным ограничивает RLS.

**Почтовая доставка не настроена:** регистрация по паролю работает сразу без проверки владения адресом, magic link и восстановление по почте недоступны. Сохраните пароль. Для публичного production-развёртывания подключите SMTP и подтверждение адресов, HTTPS и независимые резервные копии. Работоспособность инсталляции привязана к жизни этой среды, отдельный хостинг Supabase не создан.

Повторный запуск и резервная копия:

```sh
npm run supabase:start
npm run supabase:backup
npm run build
npm start
```

Конфигурация контейнеров — `supabase/selfhost/compose.yml`; проверены фиксированные версии официальных образов. Docker daemon должен работать. `npm run supabase:start` сохраняет существующие данные и ключи, ждёт health-проверок и идемпотентно применяет схему приложения.

Закрытый runtime-каталог `/workspace/food-runtime` (или `FOODLAB_RUNTIME`) содержит `.env` с уникальными случайными паролем БД/JWT-секретом, `data` с PostgreSQL, `db-config` и `backups`. Секреты создаются один раз, имеют закрытые права и не попадают в Git или инструкции среды. Если `.env` потерян, а БД существует, скрипт откажется создавать новые несовместимые ключи. `.env.local` приложения создаётся автоматически и содержит публичный anon key и внутренние адреса, а не пароль БД. Не удаляйте runtime-каталог при обновлении приложения. Снимок работающего PGDATA не заменяет согласованную резервную копию `pg_dump`; перед публикацией среды создана такая копия. Восстановление на новой машине ещё не проверено.

Проверки реального сервера: `npm run test:cloud` создаёт два временных аккаунта, проверяет CRUD и изоляцию RLS и удаляет эти аккаунты. `npm run test:e2e` дополнительно проверяет регистрацию, облачное сохранение, вход из независимого браузерного контекста и возврат к локальным данным после выхода. Облачные браузерные тесты пропускаются только там, где self-hosted runtime не настроен.

## Альтернатива: управляемый проект Supabase

Если позже решите перейти на supabase.com, удалите self-hosted параметры `NEXT_PUBLIC_SUPABASE_PROXY_PATH` и `NEXT_PUBLIC_SUPABASE_AUTH_MODE` из локальной конфигурации и выполните шаги ниже. Не удаляйте текущую БД до переноса пользователей и данных.


1. Создайте проект Supabase; выполните `supabase/schema.sql` в SQL Editor.
2. Скопируйте `.env.example` в `.env.local`. Укажите `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` (publishable или legacy anon key). Это публичный ключ, безопасность обеспечивается RLS. **Не помещайте service_role или секретный ключ в NEXT_PUBLIC_ переменные.**
3. В Auth → URL Configuration укажите адрес приложения как Site URL и разрешённый Redirect URL. Включите Email provider. Для кода OTP добавьте `{{ .Token }}` в шаблон письма, либо используйте стандартную magic link. Для production настройте SMTP и лимиты отправки.
4. Добавьте хост вашего проекта `<project-ref>.supabase.co` в разрешённые сетевые назначения облачной среды, если сеть ограничена. Не передавайте секретные значения в чат.
5. Перезапустите dev-сервер; для production пересоберите приложение: публичные переменные встраиваются во время сборки.
6. В профиле запросите письмо и войдите. Новый аккаунт начнёт с чистых данных. Для переноса локального профиля экспортируйте JSON до входа, затем импортируйте после входа.
7. Перед публикацией проверьте двумя аккаунтами: каждый видит только собственную строку; anon не читает таблицу. Не отключайте RLS для устранения ошибок.

Собственный экземпляр Supabase в этой среде проверен реальными запросами и браузерными сценариями. Управляемый внешний проект и доставка почты **не проверены**. Наличие локального профиля не означает, что создан приватный аккаунт. Ошибка загрузки БД блокирует запись, чтобы не затереть существующие данные пустым документом.

## Правила расчётов и ограничения

`КБЖУ блюда = Σ (количество × граммов в единице / 100 × КБЖУ продукта на 100 г)`.

`КБЖУ порции = КБЖУ блюда / базовые порции`.

`КБЖУ на 100 г готового = КБЖУ блюда × 100 / готовый выход`.

Вода не добавляет КБЖУ. Сырой вес не принимается за готовый. Выход стартовых блюд — оценка, подлежащая взвешиванию. Неизвестные потери жира не вычитаются. Все начальные значения продуктов усреднённые оценочные; **они не являются точными данными конкретной марки**. У каждого ингредиента есть редактируемое поле источника; используйте этикетку для нужного состояния продукта. При смене состава обновите также аллергенные категории, шаги, выход и время. При смене числа базовых порций в редакторе состав остаётся прежним; для автоматического пересчёта используйте выбор порций в просмотре.

Граммы, мл и штуки при покупках не конвертируются без данных. Поэтому одинаковые названия с разными единицами сохраняются раздельно. При добавлении одного рецепта в существующий список запасы автоматически не вычитаются — иначе они вычитались бы многократно. При генерации из меню список заменяется после подтверждения, запасы вычитаются один раз. Названия сопоставляются без учёта регистра и пробелов по краям; синонимы пока не поддерживаются.

Рекомендации — прозрачная эвристика, не ML: сходство белковой группы с положительно и отрицательно оценёнными блюдами, персональная оценка, избранное, желаемый белок, любимые специи, продукты дома; отрицательная реакция исключает рецепт. Причины оценки и заметки сохраняются для пользователя, но свободный текст автоматически не интерпретируется. Автоплан штрафует повторы рецептов и белковых групп, учитывает стоимость и ориентир калорий на основной приём. Он не гарантирует оптимум БЖУ и не заменяет полный суточный рацион. Завтраки и перекусы добавляются вручную; коктейли автоматически не записываются. Бюджет — оценка использованных продуктов, без фасовок, доставки и актуальных цен магазина.

Указанные сроки/температуры — общие ориентиры; готовность проверяйте термометром. Источники безопасности: [FoodSafety.gov — температура](https://www.foodsafety.gov/food-safety-charts/safe-minimum-internal-temperatures), [хранение](https://www.foodsafety.gov/food-safety-charts/cold-food-storage-charts). Рецепты — стартовые редакционные адаптации, не испытанные на вашей технике. Для Cook4me и аэрогриля не назначены неподтверждённые режимы; они доступны в профиле для будущих проверенных рецептов. Фото иллюстративные.

## Проверки

```sh
npm test                 # расчёты, валидация, запасы, ограничения, автоплан
npm run typecheck
npm run build
npm run test:e2e         # production-сервер запускается тестовым конфигом
```

Для E2E нужен Chromium. В этой среде `/usr/bin/chromium` уже установлен. На другой машине задайте `PLAYWRIGHT_CHROMIUM_EXECUTABLE` или установите браузер и укажите его путь. Тесты запускаются в настольном Chromium и мобильном viewport iPhone 13 (не реальный Safari). Подробные результаты текущей проверки находятся в `VALIDATION.md`.
