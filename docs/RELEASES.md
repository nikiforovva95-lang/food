- Тестовый: порт 3001, standalone `/workspace/food-releases/0.3.0-rc.1-bab957fb`, отдельный `/workspace/food-runtime-staging`.
- Сохранены также standalone-артефакты `0.2.0-rc.1-6a314e2b` и `0.2.0-rc.2-435ce2ac`, а также предыдущий кандидат `0.2.0-rc.3-ab3b99d0`; журнал — `/workspace/food-releases/index.json`.

Это работающие экземпляры внутри облачной рабочей среды. Постоянные публичные сайты и HTTPS ещё не опубликованы. Исходная версия не заменялась кандидатом.

## Работа с изменениями

1. Разрабатывать в `develop` на тестовом Supabase. Сохранять проверенные изменения отдельными коммитами и контрольными тегами.
2. При чистом закоммиченном дереве `npm run release:save` создаёт самостоятельный артефакт без секретных `.env`.
3. Для свободного тестового порта: `npm run release:run -- ID testing`. Для переключения уже работающего совместимого выпуска: `npm run release:switch -- ID testing`.
4. После проверки и одобрения пользователем конкретного кандидата можно переводить этот выпуск в основной канал. Основной и тестовый сайты должны использовать разные базы и ключи.

Скрипт переключения проверяет совместимость, делает бэкап, применяет добавочные миграции и проверяет кандидата на дополнительном порту до остановки текущего процесса. Он останавливает только процесс с подтверждённым каталогом артефакта и записью запуска. PID после перезапуска среды нельзя считать действительным без проверки.

## Возврат и данные

Проверена последовательность RC1 → RC2 → RC1 → RC3: один и тот же приватный тестовый профиль v2 сохранился при каждом переключении. Обнаруженные в ходе разработки ошибки устранены; итоговые проверки RC3 — 56 модульных и 12 браузерных без пропусков, реальные API/RLS, Docker и восстановление backup. Подробности: `../VALIDATION.md`.

Контрольная точка Git хранит код, а не содержимое PostgreSQL. Согласованные бэкапы и секреты runtime необходимо сохранять отдельно. Проверено восстановление в изолированную БД того же сервера; внешнее хранилище и перенос на другой сервер не настроены.

Исходный архив 0.1 использует формат v1. После появления документов v2 его нельзя просто включить как совместимый возврат: сервер запрещает их перезапись старым форматом. Возврат кода не должен уничтожать новые пользовательские записи. Не выполнять разрушительный Git reset, удаление runtime/томов или восстановление всей БД ради отмены интерфейсного изменения.

Реализованные возможности и внешние ограничения: `IMPLEMENTATION_V2.md`. Публикация на постоянном сервере: `../deploy/README.md`.

56 модульных и 16 браузерных проверок прошли; все восемь разделов и два экрана мастера проверены при четырёх ширинах (40 сочетаний). Новый кандидат использует ту же схему v2, основной канал не менялся. Прямой возврат именно 0.3 → 0.2 в этой задаче не запускался; сохранённые старые артефакты не удалялись. Подробнее: `DESIGN_REVIEW.md` и `../VALIDATION.md`.
