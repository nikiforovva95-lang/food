# FoodLab — тестовый выпуск пошагового меню

Новая версия разрабатывается в `develop`. Обновление интерфейса 0.3 и инструкция пользователя описаны в [DESIGN_REVIEW.md](DESIGN_REVIEW.md). `main` и архив `v0.1.0-baseline` сохраняют исходное приложение. Код и контрольные теги отправляются в GitHub. Основной экземпляр и его Supabase остаются отдельно от тестового. Это два работающих экземпляра внутри данной рабочей среды, а не два уже опубликованных постоянных HTTPS-сайта.

## Реализованные возможности

- Пошаговый мастер: цели → кухня → завтрак → обед → ужин → проверка и утверждение меню.
- Автоматическое распределение жиров/углеводов под калории и белок; ручной режим; сообщение о невозможных целях; сохранение допустимого черновика.
- Размер всей тарелки, число дней и людей, отдельное число приготовленных тарелок. Последующий приём учитывает оставшиеся КБЖУ; утверждённые блюда сами не меняются.
- Выбор из подходящего каталога, исключение конкретного предложения, другие варианты, учёт прошлых оценок, доступных продуктов, любимых специй, новизны и оценки размера порции.
- Снимки рецептов в утверждённом меню и факте еды. История меню, восстановление копии; история редакций рецептов и их восстановление.
- Рецепт на всю партию, масштабирование массы ингредиентов и масс в шагах без умножения температуры/времени; оценка готового выхода и предупреждение о загрузках/хранении.
- Запись целой личной тарелки или фактически съеденных граммов. Семейные порции не засчитываются как съеденные одним человеком.
- Покупки для всех приготовленных партий с однократным вычитанием пригодных запасов. Перенос купленных целых упаковок в запасы и списание ингредиентов при готовке — однократно для каждой операции.
- Магазины/район Краснодара, ручные цены и CSV, обычные/акционные/карточные условия, выбор имеющихся карт. Сравнение целых упаковок, остатков, числа магазинов и заданных сборов. Неизвестная часть корзины явно показана.
- Локальная адаптация рецептов с соусом, специями или свежим гарниром, реальным пересчётом состава и сохранением. Это алгоритмическая адаптация, а не работа языковой модели.
- Серверный адаптер OpenAI Responses API: авторизация, структурированная выдача, проверки ограничений и оценочных данных, сохранение только по выбору пользователя. Счётчик в PostgreSQL ограничивает новые обращения 10 попытками в день на аккаунт; повторные одинаковые успешные запросы могут обслуживаться кэшем текущего процесса.
- Проверяемый JSON-источник цен через фиксированный серверный URL или файл, кэш и фоновый worker. Ошибка сохраняет последнюю успешную загрузку и её дату; наблюдаемая дата товара не подменяется временем загрузки.
- Миграция существующих данных v1 → v2 без сброса рецептов/меню/покупок. Проверка ревизии строки защищает от конфликтующих записей двух устройств. Сервер запрещает перезапись v2 более старым форматом.
- PWA предлагает обновление и сохраняет данные перед переходом; первая установка не должна самопроизвольно перезагружать форму.
- Standalone-сборки, сведения о текущей версии, журнал артефактов, скрипты выбора совместимого выпуска, проверки кандидата до остановки текущего процесса и резервного копирования перед миграциями.

## Внешние подключения, которые ещё не считаются работающими

1. **OpenAI.** Нет предоставленного серверного `FOODLAB_AI_KEY`; реальный платный запрос не выполнялся. Адаптер проверен тестами с искусственными ответами. Ключ добавляется через безопасные настройки среды, назначение `api.openai.com`; значение не передавать в чат и не помещать в NEXT_PUBLIC-переменные. По умолчанию модель `gpt-4.1-mini`, её реальную доступность/оплату нужно подтвердить после настройки.
2. **Реальные магазинные источники.** Для Магнита и Пятёрочки получен отказ сетевой политики. В черновик среды добавлены точные адреса для дальнейшей проверки; сохранение черновика не применяет политику. Нет проверенной связи с API магазинов Краснодара. Работают ручной ввод, импорт и тестируемый контракт JSON-поставщика; автоматические реальные рыночные цены не заявляются.
3. **Постоянный публичный хостинг.** Нужны доступный сервер/хостинг и два реальных домена. `deploy/compose.json`, Caddy, генерация разных ключей, миграции и ежедневные backup-контейнеры подготовлены. Структура Compose проверена на зарезервированных example-доменах без публикации. TLS-сертификат и публичные адреса в этой задаче не получены.
4. **SMTP.** Парольная регистрация работает без письма, владение адресом не подтверждено. Письма, magic link и почтовое восстановление не настроены.

Фоновый worker не включается без настоящего источника. Синтетические фикстуры проверок не выдаются за магазинные данные и не добавляются в пользовательскую корзину.

## Запуск разработки без изменения основной версии

```sh
cd /workspace/food
npm ci
npm run supabase:staging
npm run dev -- --port 3001
```

Тестовый runtime — `/workspace/food-runtime-staging`, Auth/REST loopback 54341/54342. Основной runtime — `/workspace/food-runtime`, Auth/REST 54331/54332. PostgreSQL наружу не публикуется. Секретные runtime-файлы находятся вне Git и имеют права 0600. Не смешивайте конфигурации и не удаляйте каталоги данных при обновлении.

Production-проверка текущего исходного кода:

```sh
npm run build
npm start -- --port 3001
npm test
npm run typecheck
npm run test:e2e
npm run test:cloud
FOODLAB_RUNTIME=/workspace/food-runtime-staging npm run supabase:verify-backup
```

Браузерные тесты используют отдельный тестовый сайт, включая регистрацию и новое устройство. Живые API-тесты создают собственные временные аккаунты и удаляют их. Проверка backup восстанавливает согласованный дамп в отдельную временную БД того же PostgreSQL, сверяет документ/RLS и удаляет временную БД. Это проверка восстановления на данном сервере, не доказательство переноса на другой хост.

## Сборки и возврат

После коммита чистого дерева `npm run release:save` создаёт неизменяемый standalone-артефакт под `/workspace/food-releases/<version>-<commit>`. Сборка не содержит `.env` и не зависит от рабочего `node_modules`.

Для тестового запуска: `npm run release:run -- ID testing`. Для переключения сохранённого совместимого выпуска: `npm run release:switch -- ID testing`. Скрипт проверяет формат/совместимость, делает бэкап, применяет добавочные миграции, проверяет кандидата на отдельном порту и только затем останавливает процесс, чей PID подтверждён как принадлежащий предыдущему артефакту. Если сервер был запущен вручную, сначала остановите именно этот процесс. Основной канал выбирается явно словом `stable` и предназначен для одобренного выпуска.

Исходный архив 0.1 имеет формат v1 и собственный прежний способ запуска. После появления данных v2 его нельзя просто включить как обычный совместимый возврат. Запрет перезаписи защищает данные; допустимы возвраты между совместимыми выпусками v2. Восстановление всей БД — отдельное решение, поскольку меняет пользовательские записи.

## Источник цен и расписание

Серверные параметры: `FOODLAB_PRICE_FEED_URL` (HTTPS) или `FOODLAB_PRICE_FEED_FILE`; при необходимости отдельный `FOODLAB_PRICE_FEED_TOKEN`. Формат и deployment описаны в `deploy/README.md`. Для локального worker после настройки источника: `npm run prices:worker`; стандартный период 6 часов, `FOODLAB_PRICE_REFRESH_SECONDS` позволяет изменить его. Статус/heartbeat и следующая попытка видны в интерфейсе. Удалённые обращения идут через штатный прокси с TLS-проверкой.

Практические ограничения: пока сохраняется документ JSONB на аккаунт с историей и пределом загрузки 5 МБ; это не лимит 20 рецептов, но для больших многолетних архивов потребуется вынос истории в отдельные таблицы. Текстовые заметки сохраняются, свободный текст сам по себе не обучает модель. Состав/выход/стоимость стартовых и сгенерированных рецептов остаются оценочными до проверки источников и взвешивания. Время больших партий не гарантируется одним таймером.
