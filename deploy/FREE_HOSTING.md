# Личный FoodLab на бесплатном хостинге

Подготовленный вариант: Vercel Hobby для Next.js и Supabase Free для управляемых Auth/PostgreSQL. Адрес Vercel позволяет начать без покупки домена. Это предложение конфигурации, а не уже созданный сайт и не гарантия бессрочного бесплатного обслуживания: актуальные условия, допустимое личное использование, лимиты, приостановку неактивного проекта и доступные регионы нужно проверить в аккаунтах. Доступ к официальным страницам тарифов из текущей среды отклонён сетевой политикой; действующие квоты здесь не подтверждались.

## Подготовлено

Выполните из корня репозитория `node scripts/prepare-free-hosting.mjs`. В отдельном каталоге `/workspace/food-free-hosting/<commit>` создаются единый SQL из штатной схемы/миграций, образец переменных и манифест исходного коммита. Повторный запуск сохраняет совпадающие файлы и отказывается перезаписывать отличающиеся. Ключей, паролей и пользовательских данных в пакете нет. Сам скрипт не создаёт аккаунты, проекты или платные ресурсы.

## Что нужно от владельца

Войти в собственные аккаунты Vercel и Supabase. Доступ GitHub в этой среде уже работает, но он не предоставляет доступ к этим сервисам. Для автоматического продолжения можно назначить личные токены `VERCEL_TOKEN` и `SUPABASE_ACCESS_TOKEN` в защищённых настройках среды соответствующим API-хостам; значения не отправлять в чат. Требования сохранены отдельно от значений, без подключения токенов публикация не выполняется. Аккаунты, вход и принятие условий выполняет владелец.

## Порядок публикации после подключения доступа

1. Проверить реальные условия бесплатных планов. Не выбирать платные тарифы, апгрейды или расходы сверх лимита. Если провайдер не разрешает нужную конфигурацию бесплатно, остановить этот вариант и согласовать альтернативу.
2. Создать отдельные Supabase-проекты для основного и тестового приложения, если бесплатный план позволяет два проекта. Если доступен только один, начать с одного тестового сайта и сохранить прежний основной экземпляр отдельно; не смешивать тестовые записи с основными.
3. В SQL Editor каждого нового проекта выполнить подготовленный `supabase-setup.sql`. Этот файл включает RLS, ревизии, формат v2 и атомарную квоту ИИ. Нельзя ограничиться только исходным `schema.sql` версии v1.
4. Импортировать репозиторий `nikiforovva95-lang/food` в Vercel как Next.js, корень проекта — корень репозитория. Использовать поддерживаемый провайдером Node.js, соответствующий проверенному Node 24. Установка — `npm ci`, сборка — `npm run build`. Выходной каталог, серверные маршруты и Next.js-функции должен обрабатывать адаптер Next.js провайдера; не выбирать статический экспорт или GitHub Pages.
5. Основной сайт привязать к отдельной ветке выпуска из одобренного тега `v0.3.0-rc.1`, тестовый — к `develop`. Автоматическая публикация всех коммитов `develop` на основной адрес не подходит. Прежний `main` пока содержит исходную версию и не продвигался автоматически.
6. В каждом Vercel-проекте назначить URL и публичный ключ именно его Supabase-проекта по `hosting.env.example`. Режим Auth — `password`, канал — `stable` либо `testing`. Не назначать loopback-переменные `FOODLAB_SUPABASE_AUTH_URL`, `FOODLAB_SUPABASE_REST_URL` и старый локальный `FOODLAB_PUBLIC_ANON_KEY`. Ключ `service_role` приложению не нужен. Изменение переменных требует нового deployment.
7. Настроить Site URL/разрешённые redirect-адреса в Auth по фактически выданному HTTPS-адресу. Проверить, требуется ли подтверждение почты, и реальный вход. Почтовые функции не считать работающими без проверки настройки провайдера.
8. После успешной сборки проверить HTTPS, регистрацию, сохранение меню, вход с другого устройства, изоляцию двух аккаунтов, невозможность анонимного чтения и разделение основного/тестового проектов. Только после этого передавать пользователю фактические ссылки.

Новые управляемые базы будут пустыми. Локальные данные пользователя переносятся через экспорт/импорт приложения после входа; согласованный перенос существующих облачных данных нужно планировать отдельно. Облако текущей рабочей среды не переезжает само при публикации кода.

## Ограничения этого варианта

- Каталог, собственные рецепты, адаптации, меню, ручные цены/CSV и сохранение работают без платного ИИ. Реальные вызовы внешнего ИИ могут оплачиваться отдельно и сейчас не подключены.
- Бесконечный процесс worker и постоянный локальный каталог для кэша цен нельзя предполагать в serverless-функциях. Не включать на этом варианте источник/worker цен до переноса его состояния и расписания в подходящий сервис. Ручные цены сохраняются в пользовательском документе Supabase.
- Автоматические бэкапы PostgreSQL из Docker-конфигурации VPS не создаются в управляемом проекте сами собой. Доступные у провайдера копии и независимый экспорт нужно проверить отдельно. Бесплатный тариф может не включать требуемые резервные копии.
- Доступность сервиса, география и тарифные лимиты зависят от провайдеров. Не обходить ограничения и не обещать неограниченное бесплатное обслуживание.

После публикации: открыть фактический HTTPS-адрес в браузере телефона, создать аккаунт/войти и выбрать «На экран Домой» в меню браузера. Проверить повторный вход с другого устройства. Ссылки должны быть получены от провайдера; примерные адреса не выдавать за рабочие сайты.
