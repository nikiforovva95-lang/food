# Постоянные основной и тестовый сайты

Для личного размещения без собственного VPS подготовлен отдельный вариант: [Vercel и Supabase](FREE_HOSTING.md). Аккаунты и фактическая бесплатная доступность пока не подключены/не проверены.

Это готовая конфигурация для сервера с Docker Compose и двумя DNS-именами. В этой задаче выполнена структурная проверка Compose; публичные домены, сервер и HTTPS-сертификаты не создавались, потому что доступ к хостингу не предоставлен. Запущенные в текущей среде два экземпляра не являются независимым постоянным хостингом.

## Что входит

- Caddy завершает HTTPS и маршрутизирует два домена на основной и тестовый FoodLab.
- Для каждого сайта выделены PostgreSQL, Auth, PostgREST, отдельные ключи, внутренние сети, данные и runtime-кэш.
- Миграция схемы выполняется отдельным заданием до старта приложения.
- PostgreSQL и административные API не публикуются на внешних портах.
- Согласованные бэкапы создаются раз в сутки и проверяются `pg_restore --list`; предыдущие копии автоматически не удаляются.
- Опциональный профиль `prices` запускает фонового работника реального настроенного источника каждые 6 часов. При отсутствии источника работник откажется имитировать обновление.

## Подготовка

1. Указать два реальных домена, направленных на сервер, и открыть 80/443 для Caddy.
2. Получить проверенные immutable-сборки через `npm run release:save`. Они содержат `server.js`, клиентские файлы и worker. Для публикации выбирайте одобренный выпуск; новую доработку сначала устанавливайте только на тестовый адрес.
3. В корне репозитория выполнить `node deploy/init.mjs ОСНОВНОЙ_ДОМЕН ТЕСТОВЫЙ_ДОМЕН`. Будет создан `deploy/.env` с уникальными разными ключами. Повторный запуск не перезаписывает существующие секреты.
4. В `deploy/.env` задать абсолютные пути `FOODLAB_STABLE_RELEASE` и `FOODLAB_TESTING_RELEASE` к выбранным артефактам. Генератор указывает абсолютный путь Dockerfile, при переносе сервера его нужно актуализировать.
5. `docker compose --env-file deploy/.env -f deploy/compose.json config --quiet`, затем `docker compose --env-file deploy/.env -f deploy/compose.json up -d --build`.
6. Проверить регистрацию/вход, два разных аккаунта, сохранение и загрузку, HTTPS и доступность бэкапа. Перед новым выпуском проверить восстановление в отдельную БД. Включить SMTP и подтверждение почты перед использованием публичной регистрации как подтверждённой идентичности; текущий парольный режим адрес не проверяет и почтового восстановления не предоставляет.

В managed cloud при исходящих запросах из контейнеров нужны штатные HTTP(S)-прокси и CA. Dockerfile артефакта не скачивает npm-зависимости. Для HTTPS-запросов ИИ/цен в контейнер приложения/worker следует смонтировать публичный CA сеанса только для чтения и указать `NODE_EXTRA_CA_CERTS`, сохранив наследуемый прокси; TLS-проверку не отключать. Пример override приведён в `cloud-proxy.example.yml`. Для обычного VPS без такого прокси этот override не требуется.

## ИИ и цены

`FOODLAB_AI_KEY` задаётся только серверу и не попадает в браузер. `FOODLAB_AI_MODEL` по умолчанию `gpt-4.1-mini`; фактическую доступность и оплату нужно проверить на реальном ключе. Лимит — 10 обращений в день на аккаунт, серверный счётчик в PostgreSQL; ошибочный ответ уже вызванного провайдера также расходует попытку.

`FOODLAB_PRICE_FEED_URL` — фиксированный HTTPS-адрес проверенного JSON-источника. При необходимости токен передаётся отдельно в `FOODLAB_PRICE_FEED_TOKEN`, а не в URL. Разрешить фактический хост источника в сетевой политике. Формат — массив объектов или `{ "quotes": [...] }` с полями `name, store, city, location, packAmount, unit, price, observedAt, source, validUntil`. Опционально `condition: regular|loyalty|promo`, `conditions`. Дата наблюдения ISO UTC обязательна; время загрузки не подменяет её. Импорт не доказывает права источника объявлять товар в наличии.

Для фоновой актуализации после настройки источника: `docker compose --env-file deploy/.env -f deploy/compose.json --profile prices up -d`. В приложении видны статус процесса и время следующего запуска. До подключения реального источника автоматические магазинные цены не считаются работающими.

## Возврат выпуска

Изменять только путь артефакта соответствующего приложения; основную и тестовую БД не смешивать. Бэкап до миграции обязателен. Старый выпуск должен читать текущую схему пользовательских данных. Возврат интерфейса не требует удаления новых рецептов или восстановления всей БД. Старый формат не может перезаписать строку, уже обновлённую до v2. Для несовместимого выпуска нужен отдельный проверенный план миграции, а не сброс данных.

Не применять `down -v` как способ обновления: эта команда удаляет тома с данными и бэкапами. Независимую копию архивов и секретного `deploy/.env` следует хранить отдельно от сервера; конфигурация не создаёт внешний backup-аккаунт автоматически.
